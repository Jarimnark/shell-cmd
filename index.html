How a shell finds and runs a program

How a shell finds and runs a program

You type claude, press Enter, and something runs. Or you get command not found. This guide explains every step in between, for macOS and zsh, starting from zero.

Each chapter has something to click or type, a short quiz, and a box of safe commands to try on your own Mac. Every technical word is explained the first time it shows up, and the button is always in the top bar.

Everything here runs in your browser. The terminals on this page are simulations: nothing you type here touches your real computer.

Chapter 1

Terminal vs shell vs program

Three different things are involved when you type a command. People mix the words up all the time, so let's separate them.

The terminal: a window for text

The terminal is the app with the window you type into: Terminal.app, iTerm2, or the panel at the bottom of VS Code. Its job is small. It sends your keystrokes to whatever is running inside it, and it draws the text that comes back. It does not know what claude or git means.

The shell: the thing that reads your line

The shell is a program that runs inside the terminal. It prints the prompt (the % at the start of the line), waits for you to type a line, works out what that line means, and gets it done. On a Mac the default shell is zsh (say "zee shell").

The terminal is a phone. The shell is the receptionist on the other end. The phone only carries your voice. The receptionist is the one who understands "get me Claude" and knows which office to call.

Programs and processes

A program is a file (a named piece of data stored on disk) that contains instructions for the computer. While it sits on disk it does nothing. When the system starts carrying out those instructions, the running thing is called a process. A recipe in a book is a program. You cooking from it is a process. Two people can cook the same recipe at once: one program, two processes.

zsh is itself a program, and the zsh in your terminal window is a process. So is the terminal app.

A command is a line of words

What you type is a command. The shell cuts it into words at the spaces. The first word names what to run. The other words are arguments: extra information handed to it. In git commit -m "fix", the thing to run is git and the arguments are commit, -m and fix.

Interactive · life of a command
Starting a program is done by the kernel, the core of macOS that controls the hardware and decides which process runs when. The shell can only ask. The shell first makes a copy of itself ("fork"), and the copy asks the kernel to replace it with the new program ("exec"). You don't need the details. Remember that the shell finds the file, and the kernel runs it.
Before macOS Catalina (2019) the default Mac shell was bash, and most Linux systems still default to bash. The ideas on this site are the same there. Where a detail differs, a note like this one says so.

Try it on your Mac

All of these only read information.

% echo $SHELL
/bin/zsh

Your login shell: the shell macOS starts for you in a new terminal window. The answer is a file. zsh is a program on disk like any other.

% ps -p $$
  PID TTY           TIME CMD
 4821 ttys003    0:00.21 -zsh

$$ is the shell's own process number, so this lists the shell process you are typing into. Your numbers will differ. CMD should say zsh.

% zsh --version
zsh 5.9 (arm64-apple-darwin24.0)
% ls /nope; echo $?
ls: /nope: No such file or directory
1

$? is the exit code of the last command: the number a program hands back when it ends. 0 means it worked. Anything else means some kind of failure.

Behaviour described here was checked against zsh 5.9, the version macOS ships. The terminals on this page are simplified simulations, built to teach the idea.
