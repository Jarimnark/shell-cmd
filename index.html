How a shell finds and runs a program

How a shell finds and runs a program

You type claude, press Enter, and something runs. Or you get command not found. This guide explains every step in between, for macOS and zsh, starting from zero.

Each chapter has something to click or type, a short quiz, and a box of safe commands to try on your own Mac. Every technical word is explained the first time it shows up, and the button is always in the top bar.

Everything here runs in your browser. The terminals on this page are simulations: nothing you type here touches your real computer.

Chapter 1

Terminal vs shell vs program

Three different things are involved when you type a command. People mix the words up all the time, so let's separate them.

The terminal: a window for text

The terminal is the app with the window you type into: Terminal.app, iTerm2, or the panel at the bottom of VS Code. Its job is small. It sends your keystrokes to whatever is running inside it, and it draws the text that comes back. It does not know what claude or git means.

The shell: the thing that reads your line

The shell is a program that runs inside the terminal. It prints the prompt (the % at the start of the line), waits for you to type a line, works out what that line means, and gets it done. On a Mac the default shell is zsh (say "zee shell").

The terminal is a phone. The shell is the receptionist on the other end. The phone only carries your voice. The receptionist is the one who understands "get me Claude" and knows which office to call.

Programs and processes

A program is a file (a named piece of data stored on disk) that contains instructions for the computer. While it sits on disk it does nothing. When the system starts carrying out those instructions, the running thing is called a process. A recipe in a book is a program. You cooking from it is a process. Two people can cook the same recipe at once: one program, two processes.

zsh is itself a program, and the zsh in your terminal window is a process. So is the terminal app.

A command is a line of words

What you type is a command. The shell cuts it into words at the spaces. The first word names what to run. The other words are arguments: extra information handed to it. In git commit -m "fix", the thing to run is git and the arguments are commit, -m and fix.

What happens when you press Enter

Step through it. The rest of this site is mostly about step 3.

Interactive · life of a command
Starting a program is done by the kernel, the core of macOS that controls the hardware and decides which process runs when. The shell can only ask. The shell first makes a copy of itself ("fork"), and the copy asks the kernel to replace it with the new program ("exec"). You don't need the details. Remember that the shell finds the file, and the kernel runs it.
Before macOS Catalina (2019) the default Mac shell was bash, and most Linux systems still default to bash. The ideas on this site are the same there. Where a detail differs, a note like this one says so.

Try it on your Mac

All of these only read information.

Your login shell: the shell macOS starts for you in a new terminal window. The answer is a file. zsh is a program on disk like any other.

% ps -p $$
  PID TTY           TIME CMD

$? is the exit code of the last command: the number a program hands back when it ends. 0 means it worked. Anything else means some kind of failure.

Chapter 2

Files, folders, paths

The shell finds programs by looking for files in folders. So first we need a clear picture of how files are arranged and how you point at one.

One big tree

A directory is a container that holds files and other directories. "Directory" and "folder" are the same thing; Finder says folder, the terminal world says directory.

Everything on your Mac lives in a single tree of directories. The top of the tree is called the root and is written as a lone slash: /. Every file is somewhere below it.

A path is an address

A path is the address of a file or directory. You write the folder names you walk through, separated by slashes. /usr/bin/git means: start at the root, go into usr, go into bin, and there is git.

Absolute and relative

An absolute path starts with /. It starts from the root, so it means the same place no matter what.

A relative path does not start with /. It starts from wherever your shell is "standing" right now. That spot is the working directory. pwd ("print working directory") shows it, and cd ("change directory") moves it.

An absolute path is a full postal address. A relative path is "second door on the left": only useful if you know where the speaker is standing.

Four shortcuts

You writeIt means
/The root, the top of the tree.
~Your home directory, your personal folder. On a Mac that is /Users/yourname. The shell swaps ~ for the real path before doing anything else.
."Right here": the working directory. ./build.sh means "the build.sh in this folder".
.."One level up": the folder that contains this one.

Hidden files

A name starting with a dot, like .zshrc or .local, is hidden: plain ls and Finder skip it. Nothing else is special about it. A lot of developer tooling lives in hidden folders in your home directory, which is why ls -a ("all") will matter later.

On a Mac the default disk format ignores upper/lower case in names, so README and readme are the same file. On Linux they are two different files. Write names with the exact case anyway.

Chapter 3

Environment variables and PATH

You typed claude, not /Users/you/.local/bin/claude. So how does zsh know which folder to look in? It reads a setting called PATH.

Environment variables: named settings

An environment variable is a named piece of text that a process carries around, like HOME=/Users/you. Every process has its own set. When a process starts another one, the new process gets a copy. That is how a setting made in your shell reaches the programs you launch from it.

To read one in the shell, put a dollar sign in front of the name. zsh replaces $HOME with the value before running the command, the same way it replaces ~.

PATH: the list of folders to search

PATH is an environment variable whose value is a list of directories, separated by colons:

/Users/you/.local/bin:/opt/homebrew/bin:/usr/local/bin:/usr/bin:/bin

When the first word of your command is a plain name with no slash in it, zsh takes the folders in PATH from left to right and asks of each one: "is there a runnable file with this name in here?" The first yes wins. zsh stops and runs that file. Folders further right are never looked at.

PATH is a list of drawers you always search in the same order when you need scissors. You take the first pair you find. If there is a better pair in drawer five, you will never know, because you stopped at drawer two.

Three things follow from this rule:

  • Order matters. If two folders both contain a node, the folder that comes first in PATH decides which one you get.
  • "command not found" means the search came up empty. zsh looked in every PATH folder and none had a runnable file by that name. The program may still be on your disk, in a folder PATH does not list.
  • The folder you are standing in is not searched. That is why you run a script in the current folder as ./build.sh. The slash turns it into a path, and paths skip the search entirely.

Where PATH comes from

macOS builds a starting PATH from the file /etc/paths. Then zsh reads your personal startup files, mainly ~/.zshrc, each time a new shell starts. Installers add lines to those files, such as:

export PATH="$HOME/.local/bin:$PATH"

Read it right to left: take the current PATH, put ~/.local/bin in front of it, and store the result as the new PATH. export means "hand this variable down to programs I start". Because the new folder goes in front, it is searched first.

Editing ~/.zshrc changes nothing in terminal windows that are already open. They read the file when they started. Open a new window, or run source ~/.zshrc to make the current shell read the file again.

zsh also offers the same list as an array called path (lower case). The two are tied together: change one and the other follows. print -l $path prints one folder per line, which is easier to read.
PATH works the same way in bash and on Linux. Only the startup files differ (~/.bashrc, ~/.bash_profile), and bash has no path array.

Chapter 4

Command lookup order in zsh

Chapter 3 left something out. Before zsh searches PATH, it checks four other places. A name can be caught at any of them, and then PATH is never consulted.

The order

#zsh asksWhat that is
1Is it an alias?A nickname you (or a tool) defined, usually in ~/.zshrc: alias ll='ls -l'. zsh swaps the nickname for the longer text, then starts the lookup again with the new first word.
2Is it a shell function?A small named block of shell commands that lives in zsh's memory. Tools like nvm are shell functions, which is why which nvm prints code and not a file path.
3Is it a builtin?A command that is part of the zsh program itself: cd, echo, type, which, hash. No file on disk is involved. cd has to be a builtin: it changes the shell's own working directory, which no outside program could do.
4Is it in the hash table?zsh's memory of where it found programs before. More on this below.
5Is it in a PATH folder?The left-to-right search from chapter 3.

Words that are part of the shell language itself, like if and for, are recognised between steps 1 and 2. You will not meet them as a problem.

The practical point: if a command does something you don't expect, it may not be the program you think it is. An alias or function with the same name wins over any file.

Asking zsh what a name means

CommandWhat it tells you
type NAMEWhat zsh would run: "is an alias for…", "is a shell function", "is a shell builtin", or a file path.
which NAMEMuch the same, shorter wording. For a program it prints the path. It trusts the hash table if the remembered file is still runnable.
which -a NAMEAll matches in lookup order, with a fresh search of every PATH folder. Use this one when debugging. It shows duplicates, and it ignores the hash table.
hashPrints the hash table: every remembered name=path pair.
rehashEmpties the hash table. The next use of each command does a fresh PATH search.
Interactive · fake terminal (full lookup)

Same pretend Mac, now with all five checks. Try these in order:

  1. type ll then ll: an alias is swapped, then ls is looked up.
  2. greet and cd /: caught at function and builtin. PATH is never searched.
  3. claude twice. The second time it is found in the hash cache.
  4. alias claude='echo not the real claude' then claude, then which -a claude.

The hash table: remembering where the keys were

Searching every PATH folder on every command is wasted work, so the first time zsh finds a program it writes down the full path. Next time it goes straight there.

You found your keys in the kitchen drawer yesterday. Today you go straight to that drawer and skip the other rooms. Usually that is right. If someone moved the keys, your memory is now wrong, and that is called a stale cache.

The memory belongs to one shell process. Each terminal window has its own, and a new window starts empty. The memory goes stale when files change behind the shell's back. In zsh this shows up in two ways:

  • You keep getting the old one. You install a newer copy in a folder that is earlier in PATH. zsh still remembers the old spot, finds a working file there, and runs it. which -a lists the new one first, yet the old one runs. rehash fixes it.
  • The remembered spot is empty. zsh notices the remembered file cannot be run and quietly falls back to a full PATH search. If the program is anywhere in PATH, it still runs. If not, you get the ordinary command not found.
bash is less forgiving in the second case. It trusts its memory and stops: bash: /old/path/tool: No such file or directory, even when the tool sits elsewhere in PATH. The bash command to forget is hash -r (zsh accepts that too). The demo below lets you switch shells to see the difference.
Interactive · hash cache demo
When in doubt, run rehash or open a new terminal window. Both are harmless. Installers often tell you to "restart your terminal" for this reason, and for the PATH reason in chapter 3.

Try it on your Mac

% type cd ls git
cd is a shell builtin
ls is /bin/ls
git is /usr/bin/git

If ls says "is an alias for ls -G" or similar, something in your startup files defined that alias. That is normal.

% which -a python3
/opt/homebrew/bin/python3
/usr/bin/python3

Two or more lines means there are several copies in PATH. The top line is the one that runs.

% alias

run-help=man

Every alias in this shell. Scan it for names that match real programs.

% hash | head -5
git=/usr/bin/git
ls=/bin/ls
node=/opt/homebrew/bin/node

The first few remembered locations. The order and the list will differ. An empty result means this shell has not remembered anything yet.

% rehash

Prints nothing. It only empties the cache. It changes no files, so it is always safe.

Chapter 5

Executables and permissions

zsh found a file with the right name. Finding it is not enough. The kernel will only start it if the file is marked as runnable for you.

What counts as a program file

There are two kinds of file you can run:

  • A binary: machine code made by a compiler. go build produces one. Open it in an editor and you see garbage.
  • A script: a plain text file of commands. Its first line starts with #! (called the "shebang") and names the program that should read it, the interpreter: #!/bin/sh, #!/usr/bin/env node. When you run the script, the kernel really starts the interpreter and hands it the script.

Either one is an executable only if its execute permission is switched on. The file name does not matter. .sh or .exe endings mean nothing here.

Nine switches

Every file has an owner (a user account, normally you) and a group (a named set of accounts; on a Mac your files usually belong to the group staff). The file then carries nine on/off switches called permission bits: three actions for each of three audiences.

r = readw = writex = execute
For a filelook at the contentschange the contentsrun it as a program
For a directorylist the names insideadd, rename, delete things insidepass through it to reach things inside

The three audiences are the user who owns the file (u), the group (g), and all others (o). The system picks exactly one audience for you: if you are the owner, only the owner's three switches count.

Reading ls -l

-rwxr-xr-x  1 you  staff  4096 Nov 24 10:02 deploy.sh
│└┬┘└┬┘└┬┘  │  │    │      │        │         └ name
│ │  │  │   │  │    │      │        └ last changed
│ │  │  │   │  │    │      └ size in bytes
│ │  │  │   │  │    └ group
│ │  │  │   │  └ owner
│ │  │  │   └ number of names this file has (ignore for now)
│ │  │  └ others:  r-x  read, no write, execute
│ │  └ group:      r-x  read, no write, execute
│ └ owner:         rwx  read, write, execute
└ kind:  - file   d directory   l symlink (chapter 6)

A dash in a slot means that switch is off.

Changing them: chmod

chmod ("change mode") flips the switches. There are two ways to say what you want.

Letters: chmod +x deploy.sh turns execute on for everyone. chmod u+x only for the owner. chmod go-w turns write off for group and others.

Numbers (called octal): give each switch a value, r=4, w=2, x=1, and add them up per audience. rwx is 4+2+1 = 7. r-x is 4+1 = 5. rw- is 4+2 = 6. Three audiences give three digits: chmod 755 means rwxr-xr-x, the usual setting for programs. 644 means rw-r--r--, the usual setting for ordinary files.

Interactive · permission toggler

Why "permission denied" happens

The shell asked the kernel to run a file and the kernel said no. The common causes:

  • The execute switch is off. New files you create in an editor start as rw-r--r-- (644). So do many downloaded files. Fix: chmod +x thefile.
  • It is a directory. You cannot run a folder.
  • A folder on the way is closed to you. Without x on a directory you cannot reach anything inside it.

One detail matters for chapter 9. When you type a bare name like claude, zsh tries every PATH folder. If nothing can be run, but along the way it met something by that name that exists and is not runnable, the error is permission denied and not command not found. At the same time which -a claude says claude not found, because which only lists files that can be run. The two messages together are a strong clue: something with that name is in PATH, and it is not executable.

You can run a script without the execute switch by naming the interpreter yourself: sh deploy.sh or node cli.js. Then the program being started is sh or node, and the script only needs to be readable.
macOS has a second, separate safety check called Gatekeeper for downloaded apps ("cannot be opened because the developer cannot be verified"). That is not a permission bit and is outside this guide.
Permission bits and chmod work the same on Linux. The wording of errors differs a little: bash says bash: ./deploy.sh: Permission denied.

% ls -l /bin/ls ~/.zshrc
-rwxr-xr-x  1 root  wheel  154624 Oct 12 09:30 /bin/ls
-rw-r--r--  1 you   staff     212 Nov  3 18:41 /Users/you/.zshrc

A program (x on, owned by the system account root) next to a plain settings file (no x anywhere).

% stat -f '%Sp  %Lp  %N' /bin/ls ~/.zshrc

-rw-r--r--  644  /Users/you/.zshrc

The letters and the octal number side by side.

% id -un; id -gn

Your user name and your main group. These decide which three switches apply to you.

% ls -ld ~ ~/.local/bin
drwxr-x---+ 62 you  staff  1984 Nov 24 09:12 /Users/you
drwxr-xr-x   3 you  staff    96 Nov 20 14:05 /Users/you/.local/bin

-d shows the directory itself and not its contents. Note the leading d. A trailing + or @ means macOS keeps extra attributes on it; ignore those.

Chapter 6

Symlinks

Look inside a PATH folder and you will often find that the "programs" there are not the real files. They are pointers to files kept somewhere else. Those pointers are symlinks, and most install and update trouble involves one.

First: a name is not the file

On disk, each file is described by a record called an inode. The inode holds everything about the file except its name: where the data is, its size, its owner, its permission bits. A directory is a simple table that maps names to inodes. So a file name is a label stuck on an inode.

What a symlink is

A symlink (symbolic link) is a tiny special file whose whole content is a path to another file. That other file is the target. When any program opens or runs the link, the kernel reads the path inside and goes to the target without telling anyone.

A symlink is a sticky note on a drawer that says "the scissors are in the garage, shelf 2". The note is not the scissors. Throw the note away and the scissors are still in the garage. Take the scissors out of the garage and the note is still there, and now it lies.

Making one

ln -s  /Users/you/.local/share/claude/versions/2.1.0  /Users/you/.local/bin/claude
       └──────────── target: the real file ─────────┘  └──── link: the new name ────┘

The order is "existing thing first, new name second", the same as cp. -s means symbolic. If something already exists at the link name, ln -s refuses with "File exists". Adding -f ("force") replaces it: ln -sf. That is how you repoint an existing link.

Spotting one in ls -la

% ls -la ~/.local/bin
lrwxr-xr-x  1 you  staff  45 Nov 24 10:02 claude -> /Users/you/.local/share/claude/versions/2.1.0

Two signs: the first character is l, and there is an arrow after the name. The arrow shows the path written inside the link. The size (45) is the length of that path text. The permission letters on a symlink mean nothing; the target's permissions are what count.

Why installers love them

An installer can keep each version of a tool in its own place (versions/2.1.0, versions/2.2.0) and put a single short name in a PATH folder that points at the current one. Updating then means changing one pointer. Chapter 8 walks through that.

Broken links

If the target is deleted, moved or renamed, the link stays behind and points at nothing. This is a dangling link (or broken link). The confusing part:

  • ls -la still lists the link with its arrow and gives no warning. ls only reads the note; it does not check the garage.
  • Running it by name gives zsh: command not found. To zsh's PATH search, a link to nothing is the same as nothing.
  • Running it by full path gives no such file or directory, about a path you can plainly see in ls.

So when a command vanishes, do two checks: ls -la on the link, then ls -la on whatever the arrow points to.

The reverse case is simpler. If the link is deleted and the target is fine, the program is still on disk and only its name in PATH is gone. Recreate the link with ln -s and it is back.

Interactive · symlink playground
A target can be a relative path, like node -> ../Cellar/node/22.11.0/bin/node. It is read starting from the folder the link is in, not from where you are standing.
There is an older kind of link, the hard link: a second name attached directly to the same inode. Neither name is "the original". The number after the permissions in ls -l counts those names. Installers rarely use them, so this guide stops here.
Symlinks work the same on Linux. Linux shows a link's own permissions as lrwxrwxrwx, and ls there usually colours broken links red, which macOS does not do by default.

lrwxr-xr-x@ 1 root  wheel  11 Oct 12 09:30 /tmp -> private/tmp
lrwxr-xr-x@ 1 root  wheel  11 Oct 12 09:30 /var -> private/var

% ls -la ~/.local/bin

drwxr-xr-x  3 you  staff  96 Nov 20 14:05 .
drwxr-xr-x  5 you  staff 160 Nov 20 14:05 ..
lrwxr-xr-x  1 you  staff  45 Nov 24 10:02 claude -> /Users/you/.local/share/claude/versions/2.1.0

If you have tools installed here you will see their links. "No such file or directory" only means you have no such folder.

% readlink ~/.local/bin/claude
/Users/you/.local/share/claude/versions/2.1.0

readlink prints only the path stored in the link.

% ls -laL ~/.local/bin/claude
-rwxr-xr-x  1 you  staff  182000000 Nov 20 14:05 /Users/you/.local/bin/claude

-L tells ls to follow the link and describe the target. If the link is dangling, this is the form that fails with "No such file or directory", which makes it a quick health check.

Chapter 7

How programs get installed

"Installing" a command-line tool sounds mysterious. With what you now know, it is two plain steps:

  1. Put the program's files somewhere on disk.
  2. Make its name show up in a PATH folder. Usually that is a symlink in a folder already in PATH. Sometimes the installer adds a new folder to PATH in ~/.zshrc.

A package manager is a tool that does these steps for you, and also updates and removes software: Homebrew (brew) for general Mac software, npm for things written in JavaScript. Each one has its own favourite folders. Here are the four patterns you will meet, using claude as the example.

1. A native installer

You run an install script from the vendor's website. It downloads one self-contained binary.

~/.local/share/claude/versions/2.1.0     ← the real binary, one file per version
~/.local/bin/claude  ->  ~/.local/share/claude/versions/2.1.0     ← the name in PATH

Needs ~/.local/bin in PATH. Everything is inside your home directory, so no admin password is involved. The tool updates itself.

2. npm global install

npm install -g SOMETHING installs a JavaScript package "globally", meaning for your whole account and not for one project. npm has a setting called the prefix, a base folder. Packages go under PREFIX/lib/node_modules and their command names go in PREFIX/bin.

~/.npm-global/lib/node_modules/@anthropic-ai/claude-code/cli.js     ← the real script
~/.npm-global/bin/claude  ->  ../lib/node_modules/@anthropic-ai/claude-code/cli.js

Here the prefix is ~/.npm-global, a common custom choice. npm config get prefix tells you yours. The program is a script that starts with #!/usr/bin/env node, so it also needs a working node in PATH.

3. Homebrew

brew install keeps every package in its own versioned folder and links the commands into one shared bin.

/opt/homebrew/Caskroom/claude-code/2.0.9/claude     ← the real file
/opt/homebrew/bin/claude  ->  ../Caskroom/claude-code/2.0.9/claude

On Apple Silicon Macs the base is /opt/homebrew. On Intel Macs it is /usr/local. Homebrew's setup adds its bin to your PATH.

4. nvm: a separate world per Node version

nvm ("Node Version Manager") lets you keep several versions of Node side by side. Each version lives in its own folder with its own bin and its own global packages:

~/.nvm/versions/node/v22.11.0/bin/node
~/.nvm/versions/node/v22.11.0/bin/claude  ->  ../lib/node_modules/@anthropic-ai/claude-code/cli.js
~/.nvm/versions/node/v20.18.0/bin/node          ← no claude here

nvm use 22 works by putting that version's bin folder at the front of PATH. So a tool you installed with npm install -g while on Node 22 is only reachable while Node 22 is active. Switch to Node 20 and the command seems to vanish. It was never installed for Node 20.

Why two installs of the same tool fight

Nothing stops you from installing the same tool in two of these ways. Then:

  • Only one runs. The one whose folder is earliest in PATH. The other sits on disk, shadowed.
  • Each has its own updater. npm update -g updates npm's copy. The native tool's self-update updates the native copy. If you update the copy you are not running, the version you see does not change, which looks like "the update didn't work".
  • Uninstalling one uncovers the other. Remove the winner and an old forgotten copy suddenly answers to the name.
  • PATH order can differ between terminals. A VS Code terminal, a new tab, and a shell where you ran nvm use can each have a different order, so "it works in one window and not the other".

The cure is always the same. Run which -a NAME to see every copy. Decide which one you want. Remove the others with the tool that installed them (npm uninstall -g, brew uninstall), then rehash.

Interactive · which install wins?
On Linux the patterns are the same with different folders: system packages land in /usr/bin (installed by apt or dnf), and Homebrew on Linux lives in /home/linuxbrew/.linuxbrew.

Try it on your Mac

% which -a claude node npm
/Users/you/.local/bin/claude
/opt/homebrew/bin/node
/opt/homebrew/bin/npm

One line per copy found. More than one line for the same name means duplicate installs. "not found" is fine if you don't have that tool.

% npm config get prefix
/Users/you/.npm-global

Where npm install -g puts things. With nvm active it will be a folder under ~/.nvm/versions/node/.

% npm ls -g --depth=0
/Users/you/.npm-global/lib
├── npm@10.9.0
└── typescript@5.6.3

Every package installed globally under that prefix. Only lists; changes nothing.

% brew --prefix; brew list --versions | head -5
/opt/homebrew
git 2.47.0
go 1.23.2
node 22.11.0

Homebrew's base folder and the first few things it installed. "command not found: brew" means you don't use Homebrew.

% ls ~/.nvm/versions/node
v20.18.0  v22.11.0

One folder per Node version, each with its own globals. "No such file or directory" means you don't use nvm.

Behaviour described here was checked against zsh 5.9, the version macOS ships. The terminals on this page are simplified simulations, built to teach the idea.
